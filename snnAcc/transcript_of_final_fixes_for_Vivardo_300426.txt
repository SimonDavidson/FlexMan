  What's happening

  The weight_cache instance in weight_generator.v:386 passes IDX_ADDR_BITS = WEIGHT_IDX_SZ = 5. Substituting that into line 174:

  reg_addr[IDX_ADDR_BITS-6:0] = cache_addr_r[IDX_ADDR_BITS-1:5];
  //        └─ [-1:0]                          └─ [4:5]

  cache_addr_r is declared [IDX_ADDR_BITS-1:0] = [4:0] — descending. The part‑select [4:5] is ascending, so its direction does not match
  the declaration. That's exactly what synth 8-523 reports. The same problem exists on line 172 (shifted_index[-1:0]) and gets even worse
   for the bias/pot caches that pass IDX_ADDR_BITS=2, where every sub‑6‑bit branch is ill‑formed.

  Why Xcelium is silent

  The branch in question is slice_sz_i == 3'b000 (1‑bit elements). For the weight cache slice_sz_i is 3'b011 (8‑bit), so that case arm is
   dead code. Xcelium is happy to elaborate the unreachable case arm and only flags out‑of‑range part‑selects at run time. Vivado's
  elaborator statically checks every part‑select bound regardless of reachability.

  The bias/pot caches (IDX_ADDR_BITS=2) are even more broken — they only ever hit the 3'b011 arm but the elaborator still has to validate
   the smaller arms.

  Fixes (pick one)

  1. Guard with generate — wrap each case arm in if (IDX_ADDR_BITS >= N) ... else ... so the small‑element arms only exist whenthe
  address width can hold them.
  2. Replace the case with a shift — semantically all six arms are addr >> (5 - slice_sz_i) (or similar). A barrel shifter has no
  part‑select arithmetic and works for every IDX_ADDR_BITS.
  3. Clamp the indices — e.g. cache_addr_r[IDX_ADDR_BITS-1 : (IDX_ADDR_BITS>5 ? 5 : IDX_ADDR_BITS-1)] and pad with zeros. Ugly but local.

  Option 2 is the cleanest — it removes the entire repeated case structure on lines 166–210 (and 219–236) and leaves nothing for Vivado

 Wrap acc_snn_processor with on-chip memories                                                                                            
                                                                                                                                         
 Context                                                                                                                                 
                                                                                                                                         
 Today acc_snn_processor exposes seven raw SRAM-style memory buses (act, weight, syn_curr, bias, thresh, pot, spike). Only the testbench
  tb_acc_snn_processor.v ever attaches storage to those buses — anything outside the simulator has to drive memories off-chip. This
 change adds a self-contained synthesis-friendly wrapper that brings each memory on-chip as a 16 KB BRAM, so the design can be
 instantiated in a larger system (or on an FPGA) without external memory plumbing.

 Decisions captured from the question round:
 - Keep the existing internal syn_curr_mem arbiter (neuron_processing has fixed priority). The wrapper just attaches one sharedSRAM to
 the single syn_curr_mem_* port group exposed by acc_snn_processor.
 - New SRAM is a synthesizable inferred-BRAM module (not the testbench's sram_model).
 - Address mapping into each on-chip BRAM is a plain low-bit truncation: bram_addr = dut_addr[ADDR_W-1:0].
 - Each BRAM accepts an INIT_FILE parameter; if non-empty, it $readmemhs its contents at time 0.

 New files

 1. /home/davidsos/dev/snnAcc/sram_bram.v — a single new synthesizable single-port BRAM module used seven times by the wrapper.
 Parameters: DATA_W (default 32), ADDR_W (default 12 → 4096 entries → 16 KB at 32-bit), INIT_FILE (default ""). Inferred-BRAM pattern:
 single always @(posedge clk) block with if (we) mem[addr] <= wdata; if (re) rdata <= mem[addr]; plus an initial block that calls
 $readmemh(INIT_FILE, mem) when the string is non-empty. Registered read; one-cycle latency; matches the protocol acc_snn_processor
 already expects.
 2. /home/davidsos/dev/snnAcc/wrapped_acc_snn_processor_plus_memories.v — the wrapper.

● Diagnosis: the BRAMs have no path to a primary output, so Vivado's optimiser correctly classifies them as dead logic.         
                                                                            
  Cone-of-influence analysis on the wrapper:                                                                                    
                                                                                                                                
  The wrapper's only outputs are sys_ack_o, spike_proc_finished_o, acc_busy_o, acc_finished_o. Now trace backwards from each:   
                                                                                                                                
  - sys_ack_o — combinational decode of sys_addr_i[31:16] against TGT_CONFIG_BASE_ADDR. Doesn't touch any memory.               
  - acc_busy_o, acc_finished_o, spike_proc_finished_o — driven by control-FSM counters in spike_processing and neuron_processing
   (timestep counters, iteration counters, the running_r flag). Those counters are clocked off start_new_block_i and the        
  AXI-programmed config values; they advance based on internal handshake taken/valid lines, not on memory data.
                                                                                                                                
  So the data path act_mem → weight_mem → syn_curr → pot → spike is purely internal. Every output of every BRAM eventually goes 
  into a register that either (a) writes back into another BRAM that is also un-observable, or (b) is consumed by control logic
  that only cares whether a transaction completed, not what the data was. Vivado does a full reverse-reachability sweep:        
  anything whose output cannot affect a primary output is removed. The seven BRAMs fall out, and behind them a great deal of
  spike_processing / neuron_processing datapath collapses too. (You can confirm this by looking at the synthesis log — you'll
  see hundreds of "removed because unused" / "trim" messages, not just BRAM removals.)

  This is not a coding bug in sram_bram.v. The same code synthesises into BRAMs in any context where the output is observable.  
  The wrapper is just missing observability.
                                                                                                                                
  Three fixes, in order of cleanliness:                                                                                         
   
  1. Expose the spike output — bring spike_mem content out of the wrapper via a small read-side port (e.g. an external          
  dbg_spike_addr_i / dbg_spike_data_o pair, or a streaming readout that walks the spike memory after acc_finished_o rises). This
   is the right answer because the spikes are the design's output — without them the accelerator has no observable function.    
  Once spike_mem is observable, every datapath feeding it (pot → syn_curr → weight & act → ...) becomes live, and all seven
  BRAMs survive.
  2. Cheap "keep-alive" port — add a single dbg_data_or_o output equal to |act_mem_data | |weight_mem_data | |syn_curr_mem_rdata
   | |bias_curr_mem_data | |thresh_mem_data | |pot_mem_rdata. Vivado then can't prove any BRAM is dead. Tiny area cost;         
  preserves the BRAMs but is a hack.
  3. Synthesis attribute — annotate either each sram_bram instance or its internal mem array with (* dont_touch = "true" *) (or 
  (* keep = "true" *) on mem). This forces Vivado to keep them even with no observable path. It's the laziest fix and it leaves 
  a lot of other dead datapath logic in place that the BRAMs feed, which Vivado will still happily prune — so you'll have the
  BRAMs but starved of any consumer.                                                                                            
                                                            
  If you want, I can implement option 1 (spike read-back port) — that's the only fix that makes the wrapper usable as a real    
  accelerator endpoint, not just a synthesis target. Which would you like?
